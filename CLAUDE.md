# CLAUDE.md — Backend

## Project overview

NestJS backend for a chess web app. Handles bot play (Stockfish + Maia), real-time multiplayer via WebSocket rooms, post-game analysis, and optional auth for saved game history. Frontend (Next.js) is a separate repo and deploys separately (Vercel); this backend deploys to a single EC2 instance.

## Stack

- NestJS 12, TypeScript 6, ESM (`"type": "module"`), Vitest as test runner
- Socket.io via NestJS Gateways for real-time multiplayer
  (`@nestjs/websockets` + `@nestjs/platform-socket.io`)
- Prisma 7 + PostgreSQL — see **Database** below
- **Chess engines run as native UCI binaries, not npm packages.** Stockfish and
  Maia are spawned as child processes and driven over stdio. Maia is a set of
  Leela weights that requires the `lc0` binary and has no npm equivalent, so
  there is deliberately no engine dependency in `package.json`. Binary paths come
  from env vars — see **Deployment**.
- `chess.js` for move validation, FEN/PGN, and check/mate detection
- `class-validator` + `class-transformer` for `ValidationPipe` on DTOs. Use these
  on WebSocket move payloads especially — that is untrusted client input.
- `@nestjs/config` for env loading
- **Auth is deferred — no auth dependencies are installed.** Note that
  NextAuth/Auth.js is a Next.js-side library and *cannot run inside NestJS*; the
  frontend owns the login flow. When auth is built here, this backend's job is to
  **verify** what the frontend issues (e.g. verifying the Auth.js session JWT in
  a Nest guard), not to run Auth.js itself. Do not install NextAuth in this repo.
- pnpm (version pinned via Corepack — see `packageManager` in package.json)
- ESLint (v10, flat config) + Prettier — Prettier runs *through* ESLint via `eslint-plugin-prettier`, so formatting violations surface as `prettier/prettier` lint errors and are autofixed by `pnpm lint`. `eslint-config-prettier` is included (by the plugin's `recommended` preset) to disable stylistic ESLint rules that would conflict.

## Module system

The project is ESM: `"type": "module"`, with `module` and `moduleResolution` both
set to `"nodenext"` in `tsconfig.json`.

**Relative imports must carry a `.js` extension:**

```ts
import { AppService } from './app.service.js';   // correct
import { AppService } from './app.service';      // fails under nodenext
```

**Source files remain `.ts` — nothing is renamed, and no `.js` file is ever
authored by hand.** TypeScript deliberately does not rewrite import specifiers on
emit, and Node's ESM resolver does no extension guessing, so the specifier has to
name the file that exists at runtime (`dist/app.service.js`). `tsc` resolves
`'./app.service.js'` back to `app.service.ts` for typechecking.

NestJS 12's own packages are ESM-only (`"type": "module"` with no CJS fallback),
so this is aligned with the framework rather than a workaround.

## Database

- Prisma 7 using the **`prisma-client`** generator (not the old
  `prisma-client-js`), with `moduleFormat = "esm"` and `output` pointing at
  `src/generated/prisma`.
- That folder is **gitignored** and regenerated by the `postinstall` hook.
- **Import `PrismaClient` from `../generated/prisma/client.js`, NOT from
  `@prisma/client`.** Prisma 7 no longer generates into `node_modules`.
- `prisma7.config.ts` supplies `DATABASE_URL`, read from `.env` via dotenv.
  `.env` is gitignored.
- `PrismaModule` is deliberately **not** `@Global()` — feature modules import it
  explicitly so their DB dependency stays visible in their own metadata.
- **Current state: no models are defined and no migrations have been run.**
  `prisma/schema.prisma` contains only the generator and datasource blocks.

## Testing

- Write tests alongside each feature, not after or before (no strict TDD).
- Use Vitest + `@nestjs/testing` utilities. `globals: true` is set, so
  `describe`/`it`/`expect` need no import; use `vi.*` for mocks.
- DO NOT remove `unplugin-swc` from `vitest.config.ts`. Vitest transforms with
  esbuild, which cannot emit `emitDecoratorMetadata`; without SWC every
  `Test.createTestingModule` fails to resolve providers.
- Unit specs live next to the code (`src/**/*.spec.ts`). E2E specs live in
  `test/` and run under the separate `vitest.config.e2e.ts`.
- **Do not import from `supertest/types`** — it does not resolve under ESM (`App`
  exists only in `@types/supertest`, is not re-exported from the package root,
  and the runtime package ships no `types` module). Use a bare
  `INestApplication`.
- Prioritize testing: room state transitions, Elo-to-engine routing logic,
  move validation integration, and any WebSocket event handling.

## Deployment

- Single EC2 instance. The Next.js frontend deploys separately to Vercel.
- **The host must provide the engine binaries**: `stockfish`, plus `lc0` and the
  Maia weight files. `pnpm install` does not supply these — they belong in the
  EC2/Docker provisioning step, with their paths exposed as env vars.
- `DATABASE_URL` must be set in the environment.
- `postinstall` runs `prisma generate`, so the gitignored client is rebuilt on a
  fresh clone.
- Production entrypoint is `node dist/main.js` — the extensionless form does not
  resolve under ESM.

## Tooling gotchas

- **`prisma init` rewrites `package.json`.** It has silently deleted
  `"type": "module"` and changed `license` from `UNLICENSED` to `ISC`. Re-check
  both after running it. Pass `--no-skills` to skip the agent-skill install.
- **pnpm blocks dependency build scripts by default** (`ERR_PNPM_IGNORED_BUILDS`).
  Approved packages are listed under `allowBuilds` in `pnpm-workspace.yaml`
  (`prisma`, `@prisma/engines`, `@prisma/client`, `@swc/core`, `esbuild`, …). A
  blocked Prisma build silently skips the engine download.
- **Agent skills:** `.agents/skills/` holds the only real files;
  `.claude/skills/*` are symlinks pointing into it. Deleting `.agents/` leaves
  dangling symlinks and removes the skills.
- Observation, not yet acted on: `ts-loader`, `ts-node`, `tsconfig-paths` and
  `source-map-support` remain as devDependencies from the original Jest/webpack
  scaffold and appear to be unused now. Worth confirming before removing.

## Decision-making

- If a design decision is ambiguous (module structure, naming, where logic should live), ASK before proceeding. Do not silently pick an approach on your own.
- Ask **before** writing the code, not after. A decision surfaced once the
  implementation already exists is much more expensive to change, and a wrong
  guess means the work gets redone.
- If a request rests on a mistaken premise, say so and explain the trade-off
  rather than just implementing it as stated.
