# CLAUDE.md — Backend

## Project overview

NestJS backend for a chess web app. Handles bot play (Stockfish + Maia), real-time multiplayer via WebSocket rooms, post-game analysis, and optional auth for saved game history. Frontend (Next.js) is a separate repo and deploys separately (Vercel); this backend deploys to a single EC2 instance.

## Stack

- NestJS 12, TypeScript 6, ESM (`"type": "module"`), Vitest as test runner
- Socket.io via NestJS Gateways (`@nestjs/websockets` + `@nestjs/platform-socket.io`)
- Prisma 7 + PostgreSQL — see **Database** below
- `chess.js` for move validation, FEN/PGN, and check/mate detection
- `class-validator` + `class-transformer` for `ValidationPipe` on DTOs — use these on WebSocket move payloads especially, that is untrusted client input
- `@nestjs/config` for env loading
- pnpm (version pinned via Corepack — see `packageManager` in package.json)
- ESLint (v10, flat config) + Prettier. Prettier runs *through* ESLint via `eslint-plugin-prettier`, so formatting violations surface as `prettier/prettier` errors and are autofixed by `pnpm lint`.
- **Chess engines run as native UCI binaries, not npm packages.** Stockfish and
  Maia are spawned as child processes and driven over stdio; Maia is Leela
  weights requiring the `lc0` binary and has no npm equivalent. There is
  deliberately no engine dependency in `package.json` — paths come from env vars,
  see **Deployment**.
- **Auth is deferred, and NextAuth must never be installed here.** Auth.js is a
  Next.js-side library and cannot run inside NestJS; the frontend owns the login
  flow. This backend's job is to **verify** what the frontend issues (e.g. the
  Auth.js session JWT, in a Nest guard).

## Module system

The project is ESM: `"type": "module"`, with `module` and `moduleResolution` both
set to `"nodenext"`.

**Relative imports must carry a `.js` extension:**

```ts
import { AppService } from './app.service.js';   // correct
import { AppService } from './app.service';      // fails under nodenext
```

TypeScript does not rewrite import specifiers on emit and Node's ESM resolver
does no extension guessing, so the specifier must name the file that exists at
runtime. **Source files stay `.ts` — never hand-author a `.js`.**

## Database

- Prisma 7 using the **`prisma-client`** generator (not the old
  `prisma-client-js`), with `moduleFormat = "esm"` and `output` pointing at
  `src/generated/prisma`. That folder is gitignored and regenerated by
  `postinstall`.
- **Import `PrismaClient` from `../generated/prisma/client.js`, NOT from
  `@prisma/client`.** Prisma 7 no longer generates into `node_modules`.
- `prisma7.config.ts` supplies `DATABASE_URL`, read from `.env` via dotenv.
  `.env` is gitignored.
- `PrismaModule` is deliberately **not** `@Global()` — feature modules import it
  explicitly so their DB dependency stays visible in their own metadata.
- **No models are defined, and none should be added until persistence is actually
  wanted.** The game module is in-memory by design.

## Game module

`src/game/` is a single hotseat game, two players alternating on one board.
**No WebSockets, no engines, no auth, no persistence.** Routes live under
`/games` in `game.controller.ts`.

- **No player identity.** The server validates only that a move is legal for the
  side to move — anyone holding the game id can move for either side. Identity
  arrives with real multiplayer.
- **Games live in a `Map` in `GamesStore` and vanish on restart.**
- **`GameService` owns the rules; `GamesStore` owns storage and knows no chess.**
  When persistence lands, the store is replaced and the service is untouched.
- **`chess.js` cannot represent a resignation or an agreed draw** — those live
  outside the position, are stored on `record.outcome`, and always take
  precedence over the board. Every other ending is derived by `deriveOutcome()`
  in `game-outcome.ts`, kept a pure function so stalemate / fifty-move /
  insufficient-material / threefold are testable straight from a FEN.
- **`GameService` is deliberately not exported from `GameModule`.** Add `exports`
  when the WebSocket gateway actually needs it.
- Ports: the backend keeps Nest's default `3000` and the Next.js frontend runs on
  `3001`, so `CORS_ORIGIN` defaults to `http://localhost:3001`.

## Testing

- Write tests alongside each feature, not after or before (no strict TDD).
- Vitest + `@nestjs/testing`. `globals: true` is set, so `describe`/`it`/`expect`
  need no import; use `vi.*` for mocks.
- **DO NOT remove `unplugin-swc` from `vitest.config.ts`.** Vitest transforms with
  esbuild, which cannot emit `emitDecoratorMetadata`; without SWC every
  `Test.createTestingModule` fails to resolve providers.
- **Unit specs live in a `tests/` subfolder inside the feature folder** —
  `src/game/tests/game.service.spec.ts`, not `src/game/game.service.spec.ts`. The
  vitest `include` is `src/**/*.spec.ts`, so the subfolder needs no config change.
- E2E specs live in `test/` and run under the separate `vitest.config.e2e.ts`.
- **E2E specs must call `setupApp(app)`** from `src/app.setup.ts` after
  `createNestApplication()`, which applies none of `main.ts`'s configuration.
  Without it the test app has no `ValidationPipe` and every expected `400`
  silently passes as a `201`/`200`.
- **Do not import from `supertest/types`** — it does not resolve under ESM (`App`
  exists only in `@types/supertest`, is not re-exported from the package root,
  and the runtime package ships no `types` module). Use a bare `INestApplication`.

## Deployment

- Single EC2 instance. The Next.js frontend deploys separately to Vercel.
- **The host must provide the engine binaries**: `stockfish`, plus `lc0` and the
  Maia weight files. `pnpm install` does not supply these — they belong in the
  EC2/Docker provisioning step, with their paths exposed as env vars.
- `DATABASE_URL` must be set in the environment.
- `postinstall` runs `prisma generate`, so the gitignored client is rebuilt on a
  fresh clone.
- Production entrypoint is `node dist/main.js` — the extensionless form does not
  resolve under ESM.

## Tooling gotchas

- **`prisma init` rewrites `package.json`.** It has silently deleted
  `"type": "module"` and changed `license` from `UNLICENSED` to `ISC`. Re-check
  both after running it. Pass `--no-skills` to skip the agent-skill install.
- **pnpm blocks dependency build scripts by default** (`ERR_PNPM_IGNORED_BUILDS`).
  Approved packages are listed under `allowBuilds` in `pnpm-workspace.yaml`. A
  blocked Prisma build silently skips the engine download.
- **Agent skills:** `.agents/skills/` holds the only real files; `.claude/skills/*`
  are symlinks into it. Deleting `.agents/` leaves dangling symlinks and removes
  the skills.

## Coding style

**Named constants: an `as const` object plus a derived union type — not `enum`.**
Keys in `CONSTANT_CASE`, declaration-merged with a type of the same name so one
import gives you both the values and the type:

```ts
export const GameStatus = { IN_PROGRESS: 'in_progress', CHECKMATE: 'checkmate' } as const;
export type GameStatus = (typeof GameStatus)[keyof typeof GameStatus];
```

Enums are nominally typed, so `chess.js`'s structural unions (`Color`, `Square`) and validated DTO fields would need a cast at every boundary — and enums are not type-erasable.

**Comments: one line, using the full 180-char print width rather than wrapping
across several.** Write one only where the reasoning is not recoverable from the
code — a library quirk, an ordering constraint, a deliberate trade-off. If a
comment restates the code, delete it. Default to none.

**Types in decorated signatures must use `import type`.** Under `isolatedModules`

- `emitDecoratorMetadata`, a type used as a controller return type or parameter is
a TS1272 error when imported as a value. So: response shapes are plain `type`
aliases imported with `import type`; request DTOs are classes imported as values,
since `ValidationPipe` needs them at runtime for its metadata.

**Validate against a library's own exported constants, never a hand-rolled list
or regex** — `@IsIn(SQUARES)`, `@IsIn(Object.values(PromotionPiece))`.

**HTTP error mapping:**

- `404` — unknown resource
- `400` — malformed input, or well-formed but illegal for the current state
- `409` — an action attempted against terminal state (e.g. moving in a finished game)

## Git / commits

- Use conventional branch naming (`feat/`, `fix/`, etc) and Conventional Commits
  (`feat:`, `fix:`, `refactor:`, `test:`, etc.)
- **Do NOT commit automatically.** Leave staging and committing to me — make the
  code changes and let me review the diff.
- Keep commit messages short — a couple of paragraphs at most. The diff carries
  the detail; the message says what changed and flags the non-obvious decision.

## Pull requests

- **Assign every PR to me** (`aizazh1`) on creation — `gh pr create --assignee @me`.
- **PRs are squash-merged into `main`.** Keep a branch to one coherent slice, so
  the squashed commit reads as a single meaningful change.
- **Do NOT merge automatically.** Opening the PR is where your work stops unless
  I ask otherwise.

## Decision-making

- If a design decision is ambiguous (module structure, naming, where logic should
  live), ASK before proceeding. Do not silently pick an approach on your own.
- Ask **before** writing the code, not after. A decision surfaced once the
  implementation exists is much more expensive to change.
- If a request rests on a mistaken premise, say so and explain the trade-off
  rather than just implementing it as stated.
